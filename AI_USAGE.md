# Использование AI

Файл вёлся по ходу работы, а не писался по памяти перед сдачей: иначе забываются отклонённые варианты и развилки, а именно их задание и спрашивает.

**Принцип.** AI использовался как инструмент ускорения анализа и подготовки черновиков. Архитектурные решения, выбор технологий и любые утверждения о контракте принимались мной и только после проверки по первоисточнику: OpenAPI-схеме, документации библиотеки или типам установленного пакета (`.d.ts`). **При расхождении между ответом AI и первоисточником приоритет всегда у первоисточника** — конкретные случаи, когда это правило сработало, перечислены в разделе 3.

Отсюда формат: не «что делал AI», а какое решение принято, на каком основании и что отвергнуто.

Разбор контракта — в `OPENAPI_ANALYSIS.md`: 32 пронумерованных пункта ①–㉜ о том, где схема расходится с интуицией или с текстом задания. Ссылки вида «(⑧)» ниже указывают на них.

## 1. Какие части делались с AI

**Сплошной разбор OpenAPI-схемы.** 48 компонентных схем, 3 пути, 4 операции. AI помог пройти схему целиком и собрать перечень особенностей контракта; каждый пункт затем перепроверен мной против самой схемы. Ручной проход дал бы то же самое медленнее и с пропусками: часть находок видна только при построчном сравнении двух мест схемы — например, что `AuctionListItemTrading.status_mobile` это инлайновый enum из 6 значений, тогда как общий `TradingStatus` содержит 9.

**Находки разбора, которые я почти наверняка пропустил бы сам** — каждая иначе всплыла бы на демонстрации:

- **query-параметр `all` у `GET /bets`** — без него отменённые ставки не приходят вовсе, и требования задания «признак отменённой ставки» и «причина отмены» недостижимы в принципе;
- **`TradingStatus`: 6 значений в списке против 9 в detail** — причём текстовое описание в схеме не совпадает ни с одним из двух наборов;
- **`trading.price` и `trading.your` в списке nullable** — у карточки может не быть ни блока цены, ни блока «моя ставка»; без этого карточка падала бы;
- **шага ставки и `last_bet_with_vat` нет в DTO списка** — они существуют только в detail, и мок, пишущий их в список, противоречил бы схеме;
- **`required` объявлен у 6 схем из 48** — почти все поля DTO опциональны, отсюда правило тотализации на границе маппера, а не точечные проверки;
- **`bid_measurement_type`** — меняет смысл числа в `price.current`: цена за рейс или за километр.

**Сверка утверждений со схемой скриптом, а не глазами.** Документы проекта содержат десятки конкретных фактов вида «в `AuctionListItemTradingYour` нет поля `win`». Все они прогнаны программно по `openapi.auctions.v0.json`: перечислены поля, enum'ы, `nullable`, списки `required`, параметры операций.

**Проверка версий библиотек по реестру npm и по типам установленных пакетов**, а не по памяти модели: актуальные мажорные версии, состав `peerDependencies`, совместимость `@hookform/resolvers` с Zod v4, различие API `Grid` между мажорными версиями MUI.

**Написание кода и тестов** по уже принятым решениям, диагностика ошибок сборки и линтера, ревью качества готового кода по четырём независимым углам (переиспользование, упрощение, эффективность, глубина решения), редактирование документов.

**Принятые предложения AI — только способы, не решения.** Ниже то, где предложением был конкретный API или приём; каждое принято после проверки по первоисточнику, ни одно — «потому что так посоветовал AI»:

| Предложенный способ                                                                                   | Чем проверен                                                                       |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `createTypeScriptImportResolver` через `import-x/resolver-next` вместо строкового `{ typescript: … }` | экспорты установленного `eslint-import-resolver-typescript` v4 + прогон `eslint .` |
| `createRootRouteWithContext` для типизации контекста маршрутов                                        | `route.d.ts` пакета + `typecheck`                                                  |
| Точечные опции линтера вместо отключения правил (`allowExportNames: ['Route']`)                       | прогон `eslint .` до и после, проверка области действия по путям                   |
| Системные пропсы `Stack` перенести в `sx` (MUI v9)                                                    | `Stack.d.ts` установленного пакета                                                 |
| Путь `@mui/x-date-pickers/AdapterDateFns` вместо `AdapterDateFnsV3`                                   | список каталогов пакета                                                            |
| `defineConfig` из `vitest/config`, а не из `vite`                                                     | `typecheck` на `vite.config.ts`                                                    |
| `createLink(Button)` для типобезопасной кнопки-ссылки                                                 | воспроизведение ошибки типов на `component={Link}`                                 |
| Сверка правила округления денег с `Intl.NumberFormat('ru-RU')`                                        | прогон форматтера на `-30000.5`, `-0.5`, `1.5`                                     |

## 2. Какие решения я принял сам

**Стек в рамках свободы задания.** **Zustand** вместо MobX: клиентского состояния мало и оно точечное (режим НДС, открытость drawer'а фильтров, «моя личность»), MobX потянул бы декораторы и `observer` ради трёх сторов без единой вычисляемой величины. **MUI** — ради готовой адаптивности, пикеров дат и доступности. **notistack** — тосты. **date-fns** — даты со смещениями.

**Фильтры в URL, а не в localStorage.** Задание допускало любой из двух вариантов. Выбран URL: ссылка с фильтрами воспроизводима, работает кнопка «назад», состояние переживает перезагрузку — и именно search params требуют Zod-валидации с безопасными fallback, что задание просит отдельным пунктом.

**Метод работы — TDD.** Задание этого не требует. Решение принято потому, что контракт зафиксирован схемой и заранее разобран: ожидаемое поведение известно до написания кода вплоть до значений, а ловушки вроде «пустая строка = не отменена» (⑫) — это готовые тест-кейсы ещё до существования функции.

**Правило «чистая функция → отдельный файл + JSDoc + тест».** Из него следует, что компоненты остаются разметкой, а требование задания про «минимальные тесты на чистую логику» выполняется без e2e.

**Конвейер DTO → Mapper → ViewModel → Component** с тремя проверяемыми запретами: компонент не типизируется DTO; ViewModel не содержит опциональных полей; маппер не знает о React и потому тестируется без рендера.

**Мутационная проверка тестов.** Прежде чем считать тест написанным, реализация ломается ровно тем способом, от которого тест защищает, и прогон обязан покраснеть. Приём трижды показал, что тест не проверяет ничего.

**Обработка ошибок и загрузки:**

- глобальный `defaultErrorComponent` плюс `errorComponent` на маршрутах с данными — белого экрана быть не должно ни при каком неучтённом `undefined`;
- ошибки **запросов** остаются inline-состоянием TanStack Query и намеренно не поднимаются в boundary: сбой одного запроса не должен уносить весь экран;
- `pendingComponent` с `pendingMs`/`pendingMinMs` — без второго параметра быстрый мок даёт моргание скелетона;
- `loader` с `ensureQueryData` на detail и ставках, но **не на списке**: там loader блокировал бы навигацию при каждой смене фильтра;
- `queryOptions`-фабрики вместо инлайнового `useQuery`: один объект на все четыре потребителя — компонент, loader, prefetch, инвалидация.

**Suspense — не основной режим загрузки.** React 19 позволяет, но задание требует явные skeleton/empty/error, пагинация держится на `keepPreviousData`, а ставкам нужен `enabled: false` при `hide_bets_history` (⑪).

**Никаких рукописных DTO** — только генерация из схемы, с проверкой воспроизводимости (`npm run generate && git diff --exit-code`) перед сдачей.

**Решения по неоднозначностям контракта.** Там, где схема допускает несколько трактовок, выбор мой, и каждый зафиксирован с аргументом (та же таблица есть в README):

| Развилка                                                                | Решение                                                                                                                             |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| В какой базе НДС отправлять ставку — признака в `SetBetRequest` нет (⑧) | Всегда **с НДС**: это база `current`/`min`/`max`/`step`. В режиме «без НДС» показывается пересчёт, но отправляется базовое значение |
| `hide_bets_history` лежит в двух местах (⑩)                             | Скрытой считается, если `true` хотя бы в одном — безопасный по умолчанию вариант                                                    |
| Что скрывает `hide_points_address_and_contacts` (㉗)                    | Адреса и контакты **точек маршрута**; контакты организатора управляются непустотой `contacts[]`                                     |
| Количества участников в ответе нет (⑬)                                  | Уникальные `organization_id` среди неотменённых ставок                                                                              |
| Шаг ставки требуется в карточке, но в DTO списка его нет (㉑)           | Берётся из кэша detail после prefetch; нет в кэше — блок не рендерится. N+1 запросов ради шага не делается                          |
| `bid_measurement_type` = `null`/`Unknown` (㉚)                          | Трактуется как `PerRoute`                                                                                                           |
| `all` у `GET /bets` (㉙)                                                | По умолчанию `true`, иначе признак и причина отмены недостижимы                                                                     |
| `statuses` описан как «1–7», кодируемых значений восемь (②)             | Отправляются коды 1–8, расхождение зафиксировано                                                                                    |
| `form_type`, `replace_external_pads`                                    | Сознательно не поддерживаются: допустимых значений схема не даёт                                                                    |

**Решения по форме ставки:**

- **`bidMeasurementType` в фабрике Zod-схемы вместо `allow_counter_bets`.** Изначально я планировал передавать флаг встречных ставок, но по разбору контракта (㉘) он чисто информационный и к ограничениям цены отношения не имеет, а без единицы измерения нельзя выполнить требование «показывать цену за км» в тексте ошибки (㉚).
- **`z.number()`, а не `z.coerce.number()`.** Коэрция делает входной тип схемы `unknown`, из-за чего типы резолвера RHF перестают сходиться при строгом `exactOptionalPropertyTypes`. Поле `type="number"` и так отдаёт число или `NaN`.
- **Подсказка про базу НДС — один раз над полем, а не в тексте каждого правила.** Она нужна до того, как сработает ошибка: к моменту ошибки пользователь уже мог ввести число не в той базе.
- **Поле по умолчанию — своя последняя ставка**, а не «доступная» цена. В режиме «Изменить ставку» правка своей ставки не должна начинаться со стирания подставленного системой числа.

**Инварианты данных в моках.** `current` есть цена лучшей ставки, а `available` обязан лежать в границах `[min, max]`. Оба проверяются при сборке сида и роняют её с внятным сообщением. Причина в разделе 4.

**Навигация без бургер-меню.** Пункт назначения ровно один, и меню из одного элемента добавляет нажатие вместо того, чтобы его убрать. Активное состояние таба — `exact: true` (иначе подсветка горела бы на всех вложенных экранах и ничего не сообщала) и `includeSearch: false` (список синхронизирует фильтры в URL, поэтому со стандартной настройкой таб не подсветился бы никогда).

## 3. Какие AI-предложения были отклонены

**Рантайм-валидация ответов Zod-схемами.** Создала бы второй источник правды рядом с OpenAPI, который неизбежно разъедется со схемой, — тогда как задание требует ровно обратного. Вместо этого DTO генерируются из схемы, а слой мапперов гасит допустимые значения контракта: `Unknown` в enum'ах, пустые строки вместо `null`, строковые числа, nullable-поля. Дешевле, честнее по отношению к единственному источнику правды и лучше защищает: неизвестное значение от бэкенда не роняет страницу, а рисуется как «Неизвестно».

**Optimistic updates.** Отклонены сознательно, хотя соблазн был: задание прямо предписывает инвалидацию list/detail/bets, ответ `POST /bets` схемы не имеет (⑨), а сервер пересчитывает места всех участников, торговые статусы и продлевает время торгов — воспроизвести это на клиенте значит продублировать серверную логику. Цена ошибки высокая: показать «вы лидируете» при отклонённой по 422 ставке — худший из возможных багов в торгах.

**Два фактических утверждения AI, снятых после проверки по реестру** (оба — по памяти модели, а не по факту): «у `notistack` проблемы с peer-зависимостями на React 19» — неверно, версия объявляет `^19` явно; «актуальная версия MUI — v7» — неверно, и проверка заодно уточнила, что важен не номер, а API `Grid`.

**Юнит-тесты на утилиты моков.** Соблазн покрыть мутатор напрямую был; отклонено в пользу интеграционных тестов через реальный слой запросов. Прямой вызов мутатора подтвердил бы сам мутатор, а не связку «клиент → HTTP → мок → клиент», где живут настоящие ошибки. Решение оправдалось: ошибку «фильтры мока применялись к проекции вместо канонической сущности» поймал именно интеграционный сценарий.

**Умный сид со случайными данными.** Данные детерминированы и собраны из явных кейсов: ловушка контракта должна быть видна на демонстрации без подготовки, а случайный сид делает прогон невоспроизводимым.

**Единый «умный» форматтер цены** вида `formatPrice(value, { vatMode, measurement, fractionDigits })` — склеивал бы три независимых решения (сумма, единица, база НДС) в один нетестируемый узел. Разделено на четыре функции, каждая под своим тестом.

**`formatMoney` на `Intl.NumberFormat`.** Вывод зависит от версии ICU (какой именно пробел-разделитель), а значит тест начинает зависеть от окружения, а вёрстка — рвать цену переносом строки. Двенадцать строк своего кода дают стабильный результат.

**Три предложения по тестам — с мутационным обоснованием, а не на словах.** Разбор предлагал добавить проверки, которые не ловят ни одной мутации сверх уже существующих. Отдельно отклонено предложение объединить три теста по отдельным флагам в один «включить всё разом»: мутация подмены двух флагов местами **проходит** объединённый тест незамеченной, но **падает** на отдельном. Объединение сделало бы покрытие слабее, а не компактнее.

**Замена Zustand-стора «моей личности» на простую константу.** Технически справедливо — сеттер ни разу не вызывается. Отклонено: расхождение с задокументированным решением относить это состояние к тому же разряду, что и режим НДС, дороже нескольких строк стора.

**Слияние `mapBet` и `countBetParticipants` в один проход** ради экономии вычислений. Это разные по смыслу чистые функции с собственными тестами, а на реальном размере списка ставок выигрыш неизмерим.

**Словарь `EnumDict` для бейджа места в рейтинге.** Тот паттерн существует для enum'ов контракта с обязательным фолбэком `Unknown` (④), а место — не enum схемы, а простое правило «первое место выделено цветом».

**`enum` в TypeScript для статусов.** Не рассматривался: `erasableSyntaxOnly` их запрещает, а значения всё равно приходят строками.

## 4. Какие места я проверял особенно внимательно

**Каждое утверждение о схеме — против самой схемы.** Ни один факт о контракте не оставлен «по памяти»: имена компонентных схем (ответ списка называется `AuctionListResponseBase`, а не `AuctionListResponse`, как подсказывала аналогия), состав `required`, точные значения шести enum'ов, `pattern` полей дат. Рукописный алиас с опечаткой компилировался бы до первого запроса.

**Ловушки, которые не дают ошибки компиляции.** Каждая — отдельный тест-кейс: `status` (строки) и `statuses` (числовые коды) — разные сущности (①②); naive-время ответа не сдвигается на смещение зоны (⑮); `isMultipleOf(30000.3, 0.1)` истинно вопреки двоичной арифметике; ключ запроса ставок включает `all` (㉙); OR двух источников `hide_bets_history` (⑩).

**Версии API — против типов установленного пакета, а не против памяти.** Три поломки сборки пришли от мажорных обновлений: `AdapterDateFnsV3` больше нет, `Stack` в MUI v9 не проксирует системные пропсы, `defineConfig` с секцией `test` живёт в `vitest/config`. Каждая проверена чтением `.d.ts`. Это ровно тот класс ошибок, на котором AI ошибался при планировании, поэтому правило «сверять с реестром и с типами» соблюдалось буквально.

**Независимость тестов от таймзоны прогона.** Даты собираются из локальных компонентов, а не из ISO-строк; проверяется соответствие `pattern` схемы и сохранение момента времени. Одно замечание ревью было принято, но реализовано иначе: предложенная проверка падала бы при прогоне в UTC. Тест, зелёный только в одной таймзоне, хуже отсутствующего.

**Границы слоёв FSD.** Сторожит линтер, а не договорённость. Три стыка разрешены явно и с обоснованием: сторы режима НДС и «личности» живут в `shared/model`, потому что их читают компоненты `entities`; prefetch приходит в карточку пропом, потому что хук лежит выше по слоям; словарь городов — в `shared/config`, потому что нужен и приложению, и сиду моков. Отдельно выяснилось, что сущности одного уровня не видят друг друга — отсюда собственные типы цены у `entities/bet`, структурно совпадающие с типами `entities/auction`.

**Инварианты данных моков — после того, как два из них нарушились незаметно.** Оба дефекта нашлись только ручными торгами: `current` не совпадал с ценой лучшей ставки (на аукционе на повышение это давало «Проигрываю» при цене, равной собственной ставке), а `available` уходил на шаг ниже `min` (форма подставляла в поле заведомо невалидное значение). Ни типы, ни тесты, ни сборка этого не ловили — нарушался инвариант предметной области, о котором ни схема, ни задание прямо не говорят. Оба закреплены проверками при сборке сида.

**Что зелёный `tsc` ничего не доказывает про запуск.** Проверка велась в четыре шага: `typecheck` → `eslint` → `build` → рантайм. Первые три проходили на каркасе, который в браузере ещё не открывался ни разу.

## 5. Какие риски остались

- **Соответствие моков схеме держится на сгенерированных типах и внимании**, а не на контрактном тесте против самого JSON схемы. Моков много, и разойтись со схемой им есть где.
- **Стор моков живёт в памяти вкладки** и сбрасывается к сиду при перезагрузке страницы. Для ручной проверки это означает, что серия ставок теряется по F5.
- **Ветка модалки формы ставки (десктоп) не покрыта автотестом.** Заглушка `matchMedia` в тестах разбирает `min-width`/`max-width`, но не `max-height`, поэтому в jsdom всегда выбирается полноэкранная ветка.
- **Полный ручной прогон адаптива по всем брейкпоинтам не закрыт**, скриншотных проверок нет. Ручная проверка велась точечно — и именно она нашла оба инварианта из раздела 4 и отсутствие сквозной навигации.
- **Доступность** опирается на компоненты MUI; прогон axe и полная проверка клавиатурной навигации не делались.
- **Соответствие «статус аукциона ↔ числовой код» в схеме не описано** — это соглашение проекта, зафиксированное в одном словаре, который читают и клиент, и мок. Если бэкенд ждёт другой порядок, фильтр статусов молча вернёт не то.
- **«Моя личность» захардкожена**: эндпоинта профиля в схеме нет, поэтому `subscriber_id`/`organization_id` перевозчика фиксированы. От них зависит подсветка своей ставки.
- **Допущения из раздела 2 могут не совпасть с ожиданиями заказчика** — прежде всего база НДС для ставки и формула количества участников. Оба вынесены в README и меняются в одном месте каждое.
- **Схема допускает `Unknown` во всех enum'ах и пустые строки вместо `null`.** Защита — словари с фолбэком и нормализация на границе, но полностью исключить неизвестное значение от бэкенда нельзя, поэтому UI обязан деградировать до «Неизвестно», а не падать.
- **Разметка привязана к API `Grid` конкретной мажорной версии MUI**: понижение версии без правки разметки не скомпилируется.

## 6. Что улучшил бы при наличии ещё одного дня

- **Контрактные тесты моков.** Валидировать ответы обработчиков против `openapi.auctions.v0.json` прямо в интеграционном прогоне — тогда «мок соответствует схеме» перестаёт быть обещанием и становится красным тестом при расхождении. Это первое, что я бы сделал.
- **CI.** `npm ci && lint && typecheck && test && build` в GitHub Actions: три поломки сборки пришли от мажорных обновлений библиотек, и CI ловил бы их до того, как они дойдут до проверяющего.
- **Мутационное тестирование автоматом** (`@stryker-mutator` по `shared/lib`). Ручной приём «сломай реализацию — прогон обязан покраснеть» поймал три декоративных теста, но он не масштабируется.
- **E2E на сквозной сценарий ставки** (Playwright): ставка → детальная → список → вкладка ставок. Плюс скриншотные проверки адаптива на ключевых ширинах — сейчас это ручной прогон по десяти брейкпоинтам.
- **Доступность**: прогон axe и проверка клавиатурной навигации по форме ставки и фильтрам. Заложено «MUI даёт доступность из коробки», но это не проверено.
- **Генерация словарей enum из схемы** вместо ручных: полноту словаря гарантирует тип, но лейбл для нового значения придётся дописывать глазами.
- **Сохранение состояния моков в `sessionStorage`**, чтобы ручная сессия переживала перезагрузку страницы — сейчас серия ставок теряется по F5.
- **Расширенные фильтры и оставшиеся поля схемы** (`chat_id`, `send_deal_before_load`): заданием не требуются, но их присутствие в контракте — повод показать полноту.
