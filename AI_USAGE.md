# Использование AI

Файл ведётся **с первого коммита** и пополняется в конце каждой фазы, а не пишется по памяти перед сдачей: иначе забываются отклонённые варианты и развилки, а именно их задание и спрашивает.

Текущее состояние: **фаза 1 (каркас) закрыта, приложение запускается.** Разделы 1–6 — итоги этапа планирования, раздел 7 — итоги фазы 1 в той же шестичастной структуре, которую требует задание.

Документы этапа: `OPENAPI_ANALYSIS.md` (разбор контракта, уходит в репозиторий), `PLAN.md` и `ARCHITECTURE.md` (рабочие, в `.gitignore`).

---

## 1. Какие части делались с AI

**Разбор OpenAPI-схемы.** Схема — 48 компонентных схем, 3 пути, 4 операции. AI прошёл её сплошняком и сопоставил с текстом задания; результат — 32 пронумерованных пункта в `OPENAPI_ANALYSIS.md`. Ручной проход дал бы то же самое медленнее и с пропусками: часть находок (например, что `AuctionListItemTrading.status_mobile` — инлайновый enum из 6 значений, тогда как общий `TradingStatus` содержит 9) видна только при построчном сравнении двух мест схемы.

**Проверка черновиков плана и архитектуры против схемы.** Отдельным проходом AI сверил каждое утверждение документов с `openapi.auctions.v0.json`, распарсив её скриптом, а не глазами. Нашлось семь расхождений, из них три критичных:

| Что нашлось | Почему это важно |
|---|---|
| Не учтён query-параметр `all` у `GET /bets` | Без него отменённые ставки не приходят — требования задания «признак отменённой ставки» и «причина отмены» были недостижимы |
| План велел засеять все 9 значений `TradingStatus` в список | В списке enum из 6 значений — мок противоречил бы собственной схеме |
| MSW-мутатор писал `last_bet_with_vat` в объект списка | Поле есть только в detail; проекции списка и detail различаются составом полей |
| `bid_measurement_type` (`PerRoute`/`PerKm`) нигде не задействован | Меняет смысл цены; задание отдельно требует «цену за км» |
| `trading.price`, `trading.your`, `cargo.car` в списке nullable | Карточка падала бы на аукционе без цены |
| `required` объявлен у 6 схем из 48 | Почти все поля DTO опциональны — тотализация нужна на границе маппера, а не точечно |
| Пять расхождений между `PLAN.md` и `ARCHITECTURE.md` (пути файлов, имя сгенерированного дерева роутов, число сторов) | Два документа описывали разные проекты |

**Проверка версий библиотек по npm-реестру**, а не по памяти: актуальные мажорные версии, состав `peerDependencies`, совместимость `@hookform/resolvers` с Zod v4, различие Grid API между мажорными версиями MUI.

**Редактирование документов** после каждого принятого решения — правки вносил AI, содержание решений моё (см. раздел 2).

## 2. Какие решения я принял сам

**Стек в рамках свободы задания.** Zustand вместо MobX — точечный UI-state не требует декораторов и `observer`. MUI — ради готовой адаптивности, пикеров дат и доступности. Синхронизация фильтров через **URL search params, а не localStorage**: ссылка с фильтрами воспроизводима, работает кнопка «назад», и именно search params требуют Zod-валидации с fallback — отдельный пункт задания. Задание допускало любой из двух вариантов; выбор мой.

**Метод работы — TDD.** Задание этого не требует. Решил так, потому что контракт зафиксирован схемой и уже разобран: ожидаемое поведение известно до написания кода вплоть до значений, а ловушки вроде «пустая строка = не отменена» — это готовые тест-кейсы ещё до существования функции.

**Правило «чистая функция → отдельный файл + JSDoc + тест».** Из него следует, что компоненты остаются разметкой, а требование задания про «минимальные тесты на чистую логику» выполняется без e2e.

**Конвейер DTO → Mapper → ViewModel → Component** как центральное правило: компонент не типизируется DTO, ViewModel не содержит опциональных полей, маппер не знает о React.

**Обработка ошибок и загрузки:**
- глобальный `defaultErrorComponent` в роутере плюс `errorComponent` на маршрутах с данными — белого экрана быть не должно ни при каком неучтённом `undefined`;
- ошибки **запросов** остаются inline-состоянием TanStack Query и намеренно не поднимаются в boundary: сбой одного запроса не должен уносить весь экран;
- `pendingComponent` с `pendingMs`/`pendingMinMs` — без второго параметра быстрый мок даёт моргание скелетона;
- `loader` с `ensureQueryData` на detail и ставках, но **не на списке**: там loader блокировал бы навигацию при каждой смене фильтра;
- `queryOptions`-фабрики вместо инлайнового `useQuery`: один объект на все четыре потребителя — компонент, loader, prefetch, инвалидация.

**Suspense — не основной режим загрузки.** React 19 позволяет, но задание требует явные skeleton/empty/error, пагинация держится на `keepPreviousData`, а ставкам нужен `enabled: false` при `hide_bets_history`. Остаётся `React.lazy` для кода вне первого экрана.

**Никаких рукописных DTO** — только `npm run generate` из схемы, с проверкой воспроизводимости (`git diff --exit-code` после генерации) в чеке перед сдачей.

**Решения по неоднозначностям контракта** — там, где схема допускала несколько трактовок, выбор мой, и каждый зафиксирован с аргументом:

| Развилка | Решение |
|---|---|
| В какой базе НДС отправлять ставку (`SetBetRequest` признака не содержит) | Всегда с НДС — это база `current`/`min`/`max`/`step`; в режиме «без НДС» показываем пересчёт в подсказке, но шлём базовое значение |
| `hide_bets_history` лежит в двух местах | Историю считаем скрытой, если `true` хотя бы в одном — безопасный по умолчанию вариант |
| Что именно скрывает `hide_points_address_and_contacts` | Адреса и контакты **точек маршрута**; контакты организатора управляются непустотой `contacts[]` |
| Количества участников в ответе нет | Считаем как число уникальных `organization_id` среди неотменённых ставок |
| Шаг ставки требуется в карточке, но в list DTO его нет | Берём из кэша detail, если он прогрет prefetch'ем; иначе блок не рендерим — N+1 запросов ради шага не делаем |
| `bid_measurement_type` = `null`/`Unknown` | Трактуем как `PerRoute` |
| `all` у `GET /bets` | По умолчанию `true`, чтобы требуемые заданием признак и причина отмены были видны сразу |
| `statuses` описан как «1–7», а кодируемых значений 8 | Отправляем 1–8, расхождение фиксируем |
| `form_type`, `replace_external_pads` | Сознательно не поддерживаем: допустимых значений схема не даёт |

**Разделение документов.** Разбор контракта вынесен из плана в отдельный `OPENAPI_ANALYSIS.md`, чтобы `README`, `ARCHITECTURE`, `OPENAPI_ANALYSIS` и `PLAN` читались независимо. Он единственный из рабочих документов уходит в репозиторий: на его номера ①–㉜ ссылаются JSDoc утилит и названия тест-кейсов.

## 3. Какие AI-предложения были отклонены

Рантайм-валидация ответов Zod-схемами была отклонена, поскольку привела бы к появлению второго источника правды рядом с OpenAPI. Вместо этого DTO генерируются из OpenAPI, а слой мапперов отвечает за нормализацию допустимых значений контракта (например, Unknown, пустые строки, строковые числа, nullable-поля) и преобразование DTO в стабильные ViewModel для UI. Это сохраняет единственный источник истины и упрощает сопровождение проекта.

**Optimistic updates.** Отклонены сознательно, хотя соблазн есть: задание прямо предписывает инвалидацию `list`/`detail`/`bets`, ответ `POST /bets` схемы не имеет, а сервер пересчитывает места всех участников, торговые статусы и продлевает `stop_time` — воспроизвести это оптимистично значит продублировать серверную логику в UI. Цена ошибки высокая: показать «вы лидируете» при отклонённой по 422 ставке — худший из возможных багов в торгах.

**Два фактических утверждения AI, снятых после проверки.** Оба про версии библиотек — по памяти модели, а не по реестру:
- «у `notistack` проблемы с peer-зависимостями на React 19» — неверно, 3.0.2 объявляет `^19` явно;
- «актуальная версия MUI — v7» — неверно, актуальная мажорная другая; проверка реестра заодно уточнила, что важен не номер версии, а API `Grid`: проп `size` появился в новом Grid, в более старой мажорной версии тот же компонент назывался `Grid2`.

**Расположение request builder в `shared/api/request-builders/`.** Обсуждалось, отклонено: сборка тела запроса зависит от разобранных search params страницы списка, то есть от вышележащего слоя, и в `shared` ей нельзя по направлению зависимостей FSD. Живёт в `features/filter-auctions/lib/`.

## 4. Что я проверял особенно внимательно

**Каждое утверждение о схеме — против самой схемы.** Документы содержат десятки конкретных фактов вида «в `AuctionListItemTradingYour` нет поля `win`». Все они прогнаны скриптом по `openapi.auctions.v0.json`: перечислены поля, enum'ы, `nullable`, списки `required`, параметры операций. Ни один такой факт не оставлен «по памяти».

**Места, где задание и схема расходятся.** Это те восемь развилок из раздела 2, где неверная трактовка не даёт ошибки компиляции и всплывает только на демонстрации.

**Границы слоёв FSD.** Три стыка разрешены явно, а не «по договорённости»: стор режима НДС переехал в `shared/model`, потому что его читают entity-компоненты; prefetch приходит в карточку пропом, потому что хук живёт в `features`; словарь городов лежит в `shared/config`, потому что нужен и приложению, и сиду MSW — импорт `src/mocks` из прод-кода затащил бы тестовый дубль в бандл.

**Согласованность двух документов между собой.** После правок сверил пути файлов, имена и число сущностей — расхождений не осталось.

## 5. Какие риски остались

- **Код ещё не написан.** Всё выше — проектные решения; часть из них подтвердится или нет только на реализации. Самый вероятный кандидат на пересмотр — объём: оценка ~28 часов велика для тестового, и при нехватке времени первыми урезаются расширенные фильтры, часть сид-кейсов и интеграционные тесты.
- **MSW-стор — самая «серверная» часть проекта**: пересчёт мест в рейтинге, торговых статусов участников, продление `stop_time`. Тестами не покрывается (это тестовый дубль), проверяется сквозным сценарием вручную. Здесь же — риск разъезда двух проекций одной сущности (список против detail), поэтому они собираются двумя явными мапперами из одного источника.
- **Допущения из раздела 2 могут не совпасть с ожиданиями заказчика** — прежде всего база НДС для ставки и формула количества участников. Оба вынесены в README и меняются в одном месте каждый.
- **Строгие флаги TypeScript** (`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`) в связке с React Hook Form и MUI исторически требуют возни. Флаги включены осознанно — без них компилятор пропустит ровно те ошибки, которые описаны в разборе контракта, — но время на это заложить нужно.
- **Разметка привязана к API `Grid` конкретной мажорной версии MUI.** Понижение версии без правки разметки не скомпилируется; версия зафиксирована в `package.json` точно.
- **Схема допускает `Unknown` во всех enum'ах и пустые строки вместо `null` в пяти полях.** Защита — словари с фолбэком и нормализация на границе, но полностью исключить «неизвестное значение от бэкенда» нельзя, поэтому UI обязан деградировать до «Неизвестно», а не падать.

## 6. Что бы я улучшил при наличии ещё одного дня

- **Контрактные тесты на моки.** Проверять ответы MSW валидатором прямо против `openapi.auctions.v0.json` — тогда «мок соответствует схеме» перестаёт быть обещанием и становится красным тестом при расхождении. Сейчас это гарантируется только типами и вниманием.
- **Генерация словарей enum'ов из схемы** вместо ручных: сейчас лейблы пишутся руками, и добавленное в схему значение придётся замечать глазами.
- **E2E на сквозной сценарий ставки** (Playwright): ставка → детальная → список → вкладка ставок. Сейчас этот путь проверяется вручную по чеклисту README и одним интеграционным тестом.
- **Визуальная проверка адаптива автоматизировать** хотя бы скриншотами на ключевых ширинах — сейчас это ручной прогон по десяти брейкпоинтам.
- **Доступность** — прогон axe и проверка клавиатурной навигации по форме ставки и фильтрам. Заложено «MUI даёт доступность из коробки», но это не проверено.
- **Разобрать оставшиеся поля схемы**, которые сейчас не отображаются: `assembly`, `admitted_organizations`, `chat_id`, `send_deal_before_load`. Они не требуются заданием, но их присутствие в контракте — повод показать полноту.

## 7. Фаза 1: каркас проекта (30 июля 2026)

Фаза начиналась с рабочего на бумаге состояния: тулинг, провайдеры и общие состояния уже были написаны, но `npm run dev` не поднимался, а `eslint .` давал 131 ошибку. Разбор показал, что содержательных проблем среди них четыре, остальное — шум от одной сломанной настройки. Итог фазы: `lint`, `typecheck`, `test`, `build` зелёные, приложение открывается на `/auctions`. Полный журнал шагов — `PLAN.md`, 1.8.

**Что делалось с AI.** Диагностика: прогон `typecheck` и `eslint`, отделение причин от следствий, чтение `.d.ts` установленных библиотек вместо догадок о версиях. Дописывание каркаса по уже утверждённому дереву из `ARCHITECTURE` (маршруты, `app.component`, два провайдера, `main.tsx`, `tests/setup.ts`). Формулировки правок в этот файл и в план.

**Решения, которые принял я.**

- **Причина, а не симптом.** 110 из 131 ошибки — ложные `import-x/no-unresolved` от одной строки: `eslint-import-resolver-typescript` v4 больше не поддерживает подключение по имени. Установка пакета заново (первая гипотеза) ничего не давала — он уже стоял. Правится настройка резолвера, а не отключается правило: `no-unresolved` и `no-cycle` — единственное, что механически сторожит границы FSD, без них правила слоёв снова становятся договорённостью.
- **`baseUrl` убран, а не заглушен.** TS предлагал `ignoreDeprecations: "6.0"` — это отложить работу на мажорное обновление. `paths` заданы относительно tsconfig и работают без `baseUrl`; проверено тем, что smoke-тест импортирует `@/app/app.component`.
- **Два ослабленных правила ESLint — точечно и с обоснованием**, а не «линтер мешает»: `allowExportNames: ['Route']` только для `src/routes/**` (экспорт `Route` обязателен для file-based маршрутов) и `only-throw-error` с разрешением `Response`/`NotFoundError` (`throw redirect()` / `throw notFound()` — штатный поток управления роутера, он будет во всех loader'ах фаз 4–7). Оба сужены до конкретных типов и путей, чтобы «бросить что попало» по-прежнему было ошибкой.
- **`RouterContext` вынесен в отдельный файл.** Документация TanStack держит тип контекста в `__root.tsx`, но тогда `router.ts → route-tree.gen → __root → router.ts` — цикл, который ловит `no-cycle`. Выбор был: отключить правило или разорвать цикл третьим файлом. Отключать правило ради одного случая нельзя — оно и нужно, чтобы циклы не завелись в фазах 5–8, где слоёв станет вдвое больше.
- **Smoke-тест раньше плана.** По плану интеграционные тесты — фаза 9. Каркас, подтверждённый только компиляцией, не подтверждён ничем: порядок провайдеров и поднятие роутера ломаются в рантайме. Пятнадцать строк теста заменяют ручную проверку в браузере после каждой правки.
- **`main.tsx` без `!`.** Шаблон Vite пишет `getElementById('root')!`. `no-non-null-assertion` в проекте — error (1.3), исключений для точки входа не делаю: явная проверка с внятным сообщением честнее.
- **Отложил то, что не нужно сейчас:** router devtools (нет пользы до реальных маршрутов, ставятся в фазе 4), `date-fns-tz` (нужен с фазы 2). Оба зафиксированы как незакрытые пункты критерия готовности фазы, а не забыты.

**Что было отклонено.**

- **Гипотеза «не хватает пакета».** Первое очевидное объяснение ошибки резолвера — отсутствующая зависимость; проверка `node_modules` показала, что пакет установлен, и версия v4 сама и была причиной. Урок общий: сообщение «invalid interface» — про интерфейс, а не про наличие.
- **Заглушить `strictNullChecks`-ошибки отключением правил.** Четыре правила требовали флага; правильный размер правки — одна строка `"strict": true` во втором tsconfig, а не четыре `off`.
- **`ignoreDeprecations` для `baseUrl`** — см. выше.
- **Форматирование всего репозитория.** `prettier --check` ругается на `AI_USAGE.md`, `OPENAPI_ANALYSIS.md` и схему OpenAPI. Схему не форматирую принципиально: она источник правды и приходит извне, её диффы не должны быть моими. Документы — отдельным решением, не попутно с починкой сборки.

**Что проверял особенно внимательно.**

- **Версии API против `.d.ts`, а не против памяти.** Три поломки фазы — от мажорных обновлений: `AdapterDateFnsV3` больше нет, `Stack` в MUI v9 не проксирует системные пропсы (`alignItems`, `flexWrap` — только через `sx`), `defineConfig` с секцией `test` живёт в `vitest/config`. Каждая проверена чтением типов установленного пакета: `ls @mui/x-date-pickers`, `Stack.d.ts`, `NotFoundRouteProps`. Это ровно тот класс ошибок, на котором AI ошибался ещё на этапе планирования (раздел 3), поэтому правило «сверять с реестром и с типами» соблюдалось буквально.
- **Что зелёный `tsc` ничего не доказывает про запуск.** Проверка велась в четыре шага: `typecheck` → `eslint` → `build` → рантайм (dev-сервер + smoke-тест). Первые три проходили на каркасе, который в браузере ещё не открывался ни разу.
- **Каждое ослабление правила — по месту применения.** Оба override'а ограничены путями и типами; в файлах фаз 5–8 они не действуют.

**Риски, которые остались.**

- **MUI v9 и системные пропсы.** В фазе 1 правка коснулась двух компонентов, но разметка фаз 5–7 — это десятки `Stack`/`Box`. Писать сразу через `sx`; иначе фаза 5 начнётся с той же ошибки, умноженной на количество компонентов. Пункт добавлен в риски плана.
- **`Grid` из раздела 5 никуда не делся** и остаётся непроверенным: адаптивная сетка списка появится в фазе 5, API `Grid` в установленной мажорной версии ещё не трогали.
- **Строгие флаги TS в связке с RHF и MUI** — риск из раздела 5 подтверждён частично: `exactOptionalPropertyTypes` уже потребовал `onRetry?: (() => void) | undefined` в `ErrorState`. Форма ставки (фаза 8) — главное испытание впереди.
- **Заглушка `/auctions` — временная и легко забываемая.** Маршрут рендерит `EmptyState` с текстом про каркас; он существует, потому что на `/auctions` ссылаются `NotFound` и `RouteError`. Снимается в фазе 5.
- **Воспроизводимость сгенерированных типов ещё не доказана.** `npm run generate && git diff --exit-code` — часть чека перед сдачей (1.3), но пока `src/` не в индексе, проверка бессмысленна: первый осмысленный прогон — после коммита фазы 1.

**Что улучшил бы при наличии ещё одного дня** (в дополнение к разделу 6).

- **Поднять версионные поломки на уровень CI.** Три ошибки фазы — от мажорных обновлений библиотек; `npm ci && npm run lint && typecheck && test && build` в GitHub Actions ловил бы их до того, как они дойдут до проверяющего.
- **Проверять error boundary тестом, а не руками.** Маршрут, бросающий ошибку в рендере, и тест на то, что виден `ErrorState`, а не белый экран — критерий готовности фазы 1 сейчас подтверждён одноразовой ручной проверкой.
- **Довести `format:check` до зелёного** — отформатировать документы, исключив схему OpenAPI из `.prettierignore`-периметра осознанно, а не оставлять чек красным до сдачи.
