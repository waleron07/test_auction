# Анализ OpenAPI-схемы: 32 ловушки контракта

Разбор `openapi/openapi.auctions.v0.json` до написания кода. Документ отвечает на один вопрос: **где схема и текст задания расходятся с интуицией — и какое решение принято**.

Источники: `ТЗ.md` (требования, дословная расшифровка `Тестовое_задание.pdf`) и `openapi/openapi.auctions.v0.json` (контракт). При расхождении задания и схемы по части контракта — прав контракт; принятое решение фиксируется здесь и повторяется в README.

Схема: OpenAPI 3.0.0, «API для UL - Auctions», 48 компонентных схем, base URL `/api/v1/`, 3 пути / 4 операции. Авторизации не объявлено (`security: null`), но 401 присутствует в ответах всех операций.

## 1. Ловушки схемы (①–⑳)

Каждый пункт ниже — источник бага, если действовать «по интуиции».

**① `status` в фильтре — НЕ статус аукциона.** Самая дорогая ловушка. В `AuctionListRequest`:
| Поле | Что фильтрует | Тип |
|---|---|---|
| `status` | **торговый статус пользователя** | `string[]` (enum-имена) |
| `mobile_statuses` | тот же торговый статус | `integer[]` (дубль `status`) |
| `statuses` | **статус аукциона** | `integer[]`, коды 1–7 |
Задание перечисляет «status» и «statuses» как два разных фильтра — именно потому, что это разные сущности. В UI подписываем однозначно: «Мой статус в торгах» и «Статус аукциона». Используем `status` (строки) и `statuses` (числа); `mobile_statuses` не шлём, чтобы не конфликтовать.

**② Числовые коды статуса аукциона нужно маппить руками.** `statuses` принимает числа, но enum `AuctionStatus` — строки. Заводим единый двусторонний словарь `AUCTION_STATUS_CODE: Record<AuctionStatus, number>` (Planning 1 … Canceled 8). Внимание: описание `statuses` говорит «1–7», а enum `AuctionStatus` содержит 9 значений — 8 кодируемых (`Planning` = 1 … `Canceled` = 8) плюс `Unknown`, у которого кода нет и который в фильтр не уходит. Отправляем 1–8, расхождение фиксируем в README.

**③ Enum'ы рассинхронизированы между схемами.** `TradingStatus` (общая схема, detail) — **9 значений**: `NotParticipating, Leading, Losing, OnPending, Confirmed, ChoosingWinner, Winner, Accepted, Unknown`. Инлайновый enum `AuctionListItemTrading.status_mobile` — **6 значений** (нет OnPending/ChoosingWinner/Accepted). Текстовые описания в обоих местах перечисляют вообще 6 и не совпадают с enum'ом. **Решение:** словарь лейблов строится по расширенному (9-значному) набору, а рендер идёт через `getTradingStatusLabel(v)` с фолбэком на `Unknown` для незнакомого значения. То же для `auc_type`: `AuctionType` содержит `Unknown`, а enum фильтра `auc_type` — только 4 значения без `Unknown` (фильтровать по Unknown нельзя, отображать — нужно).

**④ Во всех enum'ах есть `Unknown`.** Ни один `switch` по enum не пишется без ветки по умолчанию. Правило: enum → лейбл только через словарь-функцию с фолбэком, никаких прямых `enum[value]`.

**⑤ `auc_type` в фильтре — массив**, не скаляр. UI — мультиселект.

**⑥ Пагинация — `page` / `per_page`; ответ обёрнут: `{ data: [], meta }`.** `meta` = `current_page, from, last_page, per_page, to, total`. Общее число страниц берём из `last_page`, не вычисляем сами.

**⑦ Цены везде парами `*_with_vat` / `*_no_vat`.** `AuctionShowTradingPrice` даёт 6 пар: `start`, `current`, `available`, `min`, `max`, `step` — и каждая имеет `_no_vat`-близнеца, **все nullable**. Плюс `price_per_km` (= `current_price_no_vat / distance`, 0 при distance = 0). Отсюда — сквозной тумблер «с НДС / без НДС» в Zustand: он выбирает, из какой половины пары читать. Один селектор `selectPrice(price, vatMode)`, компоненты не выбирают поле сами.

**⑧ `SetBetRequest` содержит только `price` — и в самом запросе признака НДС нет.** `price` — единственное поле, `required`, ограничение «> 0» живёт **только в описании** (ни `minimum`, ни `exclusiveMinimum` в схеме нет — значит серверную проверку в моке пишем сами, а не полагаемся на «схема обязана»).
При этом было бы неверно сказать, что схема про НДС молчит: в ответах есть `trading.is_last_bet_with_vat` (nullable) и пара `red_bet_with_vat` / `red_bet_no_vat` — то есть база НДС ставки на бэкенде **отслеживается**, просто в теле запроса не передаётся и, судя по всему, определяется на стороне сервера по настройкам организации.
**Решение:** форма всегда отправляет цену **с НДС** (это база `current`/`min`/`max`/`step` без суффикса), при активном режиме «без НДС» показывает пересчёт в подсказке, но шлёт базовое значение; в подписи под полем явно сказано, в какой базе уходит число. MSW при записи ставки выставляет `is_last_bet_with_vat: true` — чтобы мок не противоречил собственному ответу. Допущение фиксируется в README и AI_USAGE как принятое кандидатом решение при неоднозначности схемы.

**⑨ Ответ `POST /bets` не имеет схемы** — в спеке буквально «ответ проксируется от upstream». Значит **на тело ответа нельзя опираться**: после успеха обязательна инвалидация detail/bets/list, а не оптимистичное чтение результата. Это подтверждает требование задания об инвалидации.

**⑩ `hide_bets_history` лежит в двух местах:** `AuctionShowResponse.hide_bets_history` (корень) и `AuctionShowTrading.hide_bets_history`. Считаем историю скрытой, если **любой** из них `true` (безопасный по умолчанию вариант). Логика — в маппере `permissions`, а не в компоненте.

**⑪ Скрытие истории не имеет серверного кода ответа.** У `GET /bets` в ответах только 200/401/404/503 — никакого 403. Значит `hide_bets_history` — чисто клиентское решение по данным detail. **Следствие для архитектуры:** страница ставок обязана грузить и detail тоже (он и так в кэше после списка/детальной), а запрос ставок — включать `enabled: !hidden`, чтобы не дёргать эндпоинт зря.

**⑫ Отменённой ставки как булева поля нет.** Есть `is_rejected: boolean` и `cancel_reason: string`, где **пустая строка = не отменена** (не null!). Признак отмены = `is_rejected || cancel_reason !== ''`. Схема вообще активно использует «пустую строку вместо null»: `contact_phone`, `organization_name`, `cancel_reason`, а `run_number: 0` = не задан. Маппер нормализует эти псевдо-пустые значения в `null` на границе, дальше UI работает единообразно.

**⑬ Количества участников в ответе ставок нет.** `BetListResponse` = `{ bets: BetItem[] }`, и только. Задание требует показать «количество участников» — **вычисляем**: число уникальных `organization_id` среди неотменённых ставок. Формула документируется в README, чтобы не выглядела как выдумка.

**⑭ Есть флаг `hide_places`,** которого нет в тексте задания, а `BetItem.place` — nullable. При `hide_places` колонка «Место» не рендерится вовсе; при `place === null` — прочерк. Добавляем в `permissions` пятым флагом.

**⑮ Асимметрия дат.** Фильтры запроса требуют ISO 8601 **со смещением** и валидируются строгим `pattern` (`...T..:..:..(±HH:MM|Z)`). А в ответах `start_time`, `stop_time`, `created_at` приходят **без смещения** («2026-05-25T16:03:00»). Отсюда два разных хелпера: `toApiDateTime(date)` (сериализация со смещением, под regex схемы) и `parseApiDateTime(str)` (разбор naive-времени как локального). Оба покрываются тестами — это самый вероятный источник тихого бага в ±3 часа.

**⑯ Формат ошибок жёстко задан.** `ProblemDetail` = `{ code, title, message, trace_id? }` для 401/404/503. `ValidationProblem` (422) = то же плюс `code: "validation_failed"` и `errors: [{ field, message, code? }]`, где `field` — snake_case-путь с точками для вложенности. HTTP-код в теле не дублируется. Значит: маппер `field → имя поля формы` (для ставки поле одно — `price`), а ошибки по неизвестным полям складываются в общий алерт, а не теряются.

**⑰ 401 и 503 есть у всех четырёх операций.** Обрабатываем оба: 401 — экран «Сессия истекла», 503 — «Сервис недоступен, повторить». Не сваливаем всё в общий «Ошибка».

**⑱ Идентификатор в маршруте.** Путь — `/auctions/{auctionUuid}`, но в теле `main` есть `id: integer` и `order_uid: string`. UUID для роутинга — `order_uid`; `id` используется только для сопоставления (`BetItem.auction_id`). В моках связь `order_uid ↔ id` держим консистентной.

**⑲ Справочника городов в API нет.** Есть `load_city` (строка), `load_gc_id` (integer), `load_range` (радиус, км) и симметричная тройка для выгрузки. Эндпоинта городов схема не содержит — подтверждает формулировку задания «из мок-словаря городов»: словарь наш, и он должен давать пару «название + gc_id».

**⑳ Фильтров в схеме сильно больше минимума из задания.** Сверх обязательных доступны: `weight_from/to`, `volume_from/to`, `body_types[]`, `is_international_shipment`, `is_favorite`, `customer`/`customer_ids[]`, `contractor`, `auction_ids[]`, `load_range`/`unload_range`, даты выгрузки/создания/начала/окончания торгов, `price_per_km_from/to`, `sort` (объект «поле → asc|desc»), `is_oldest`. **Решение:** обязательный минимум — в основной панели; расширенные — в сворачиваемой секции «Ещё фильтры». Все проходят через ту же Zod-схему search params.
Два поля сознательно **не поддерживаем**: `form_type` (описание «Тип формы», допустимых значений схема не даёт — угадывать нечего) и `replace_external_pads` («Заменять внешние площадки» — поведение внешней системы, в UI без бэкенда смысла не несёт). Оба остаются в сгенерированных типах, но в UI и в request builder не попадают; отказ фиксируется в README, чтобы не выглядел как недосмотр.

## 2. Конфликты текста задания со схемой (㉑–㉘)

Задание перечисляет поля, которых в соответствующем DTO нет. Это не ошибки задания — это места, где кандидат обязан принять решение и уметь его объяснить. Каждое такое решение кандидат обязан уметь объяснить на защите.

**㉑ «Шаг ставки» в карточке списка показать нечем.** Задание требует шаг ставки на карточке, но `AuctionListItemTradingPrice` содержит **только** `start`, `current`, `current_no_vat` — ни `step`, ни `min`/`max`. Шаг существует лишь в detail (`AuctionShowTradingPrice.step`).
**Решение:** карточка рендерит шаг из кэша TanStack Query, если detail уже загружен — а prefetch по hover (требование задания) как раз его туда и кладёт. Нет в кэше — блок шага не рендерится, без «—» и дёрганья лейаута. N+1 запросов ради шага не делаем. Компромисс документируется.

**㉒ Признака победителя в карточке нет.** `AuctionListItemTradingYour` = `{ bet, last_bet }`, поля `win` нет (в detail — `your.win` есть). В карточке победа определяется по `trading.status_mobile === 'Winner'`.

**㉓ Тумблер НДС в списке работает частично.** В списке есть только `current_no_vat`; у `start` пары без НДС нет. В режиме «без НДС» показываем `current_no_vat`, для остальных значений — базовое с пометкой. Полный пересчёт — только на детальной.

**㉔ Названия груза в detail нет.** `AuctionShowCargo` не содержит `name` (оно есть в `AuctionListItemCargo.name` и в `RoutePointCargo.name`). На детальной название груза собираем из точек маршрута `routes[].cargo.name`, при расхождении — перечисляем по точкам.

**㉕ Разнотипица одних и тех же величин.** `AuctionListItemCargo.weight/volume` — `number`, а `RoutePointCargo.weight/volume/length/width/height` — **`string`**. `AuctionShowCargo.price` — **`string`**, при этом `currency` — `integer`, а в `AuctionShowPayment.currency_code` — `string`. Нужен нормализатор `toNumber(value)` на границе маппера + единый резолвер валюты. Под тестами.

**㉖ Скрытие организатора — ещё один флаг, которого нет в задании.** `AuctionListItemOrganizer.is_hide_organization` (в списке) и `AdmittedOrganization.hide_me` (в допущенных организациях). При этом у `AuctionShowOrganizer` такого флага **нет** — асимметрия список/детальная. Добавляем в `permissions` шестым пунктом `hideOrganization`; на детальной, где флага нет, организатор показывается всегда (фиксируем как следствие контракта, а не как недосмотр).

**㉗ «Контакты» — это два разных объекта.** `AuctionShowResponse.contacts[]` (`Contact`: name/phone/work_phone/email/uid, всё nullable) — контакты организатора. `RoutePoint.contact` (`RoutePointContact`: name/phone) — контакт на точке маршрута. Флаг называется `hide_points_address_and_contacts` — по имени он относится к **точкам**, то есть скрывает `RoutePoint.location.loading_address` и `RoutePoint.contact`. Контакты организатора им не управляются, они просто могут прийти пустым массивом.
**Решение:** флаг скрывает адреса и контакты точек; блок контактов организатора рендерится по непустоте `contacts[]`. Трактовка явно описывается — это ровно тот «контакты, если они не скрыты» из задания.

**㉘ Встречные ставки в задании не упомянуты, в схеме есть.** `AuctionShowTrading.allow_counter_bets` и `BetItem.is_counter`. Рендерим чипом «встречная» в списке ставок — дешёвое соблюдение контракта.

## 3. Найдено при сплошной сверке схемы (㉙–㉜)

Четыре пункта, которые первый проход разбора пропустил. Первые два — прямое требование задания, вторые два ломают код в рантайме.

**㉙ У `GET /bets` есть query-параметр `all` — и без него отменённых ставок в ответе не будет.** Схема: `all: boolean|null`, «Вернуть все ставки аукциона, **в том числе отменённые**». Задание при этом требует показать «признак отменённой ставки» и «причину отмены» — то есть **без `all` эти требования недостижимы в принципе**, ветка UI останется мёртвой.
**Решение:** параметр обязателен в четырёх местах сразу, иначе рассинхрон: (1) сигнатура `getAuctionBets({ auctionUuid, all })`; (2) **query key** `auctions.bets(uuid, { all })` — иначе два разных ответа лягут в один кэш; (3) MSW-handler читает `all` из `request.url.searchParams` и при `all !== 'true'` отфильтровывает отменённые (признак — по ⑫); (4) в UI — переключатель «Показывать отменённые», по умолчанию **включён**, чтобы проверяющий видел требуемые заданием признак и причину отмены сразу, без лишних кликов. Инвалидация после ставки бьёт по префиксу `auctions.bets(uuid)`, накрывая оба варианта параметра.

**㉚ `bid_measurement_type` меняет смысл цены — «за рейс» или «за км».** `BidMeasurementType` = `PerRoute` (0) / `PerKm` (1) / `Unknown`, лежит и в списке (nullable), и в detail. Игнорировать нельзя: при `PerKm` число в `price.current` и `price.step` — это цена **за километр**, а задание отдельным пунктом требует показывать «текущую цену, цену за км, шаг ставки».
**Решение:** единица измерения — часть отображения цены, а не отдельный бейдж: `formatPrice` получает единицу и рендерит «30 000 ₽ за рейс» / «199 ₽/км». Та же единица подставляется в подсказки формы ставки и в сообщения Zod-схемы. `null` и `Unknown` → трактуем как `PerRoute` (базовый случай) и помечаем в README как принятое допущение. Чистая функция `resolve-price-unit.util.ts` под тестом.

**㉛ В списке `trading.price`, `trading.your` и `cargo.car` — nullable.** В `AuctionListItemTrading` оба поля объявлены как `oneOf` + `nullable: true`, `AuctionListItemCargo.car` — тоже, а в detail `CarRequirements` помечена `nullable` на уровне самой схемы. То есть у карточки может **не быть блока цены вовсе** и не быть блока «моя ставка».
**Следствие:** `resolvePrimaryAction` читает `your?.bet` (а не `your.bet`) и обязан иметь ветку «данных о торгах нет» → «Смотреть ставки»; `map-auction-card` возвращает `price: null` вместо выдуманного нуля, карточка в этом месте рисует прочерк. Оба случая — обязательные тест-кейсы, а не «на всякий случай». Сид содержит по одному аукциону с `price: null` и с `your: null`.

**㉜ `required` объявлен ровно в 6 схемах из 48 — остальное в сгенерированных типах опционально.** `required` есть только у `AuctionShowResponse` (9 полей), `BetListResponse`, `SetBetRequest`, `ProblemDetail`, `ValidationProblem`, `ValidationError`. Всё прочее — включая `main.cargo_num`, `trading.status`, `bets[].price_with_vat` — `openapi-typescript` сгенерирует со знаком `?`.
В связке с включёнными `exactOptionalPropertyTypes` и `noUncheckedIndexedAccess` (PLAN 1.2) это значит: **тотализировать нужно каждое поле DTO, а не только «странные»**. Отсюда правило границы — ни один компонент не получает DTO напрямую; маппер обязан вернуть ViewModel, где каждое поле либо заполнено, либо явно `null`, и тип ViewModel — без `?`. Это же снимает соблазн писать `item.main!.cargo_num`: `!` запрещён линтером.
Отдельный частный случай: `AuctionShowResponse.hide_bets_history` **не входит** в список `required` — значит OR из ⑩ складывает `boolean | undefined` с `boolean | undefined`, и `map-auction-permissions` обязан отдавать строгий `boolean`. Тест на «оба undefined → false» входит в набор.
